## 本次可以核实的修改

| 项目 | 修改与证据边界 |
|---|---|
| 现场采集 | `inspect` 使用标准库、只读 Docker inspect/exec、HTTP GET、npu-smi；不加载模型、不请求生成、不重启服务 |
| 参数漏采 | 旧工具只读 Docker Cmd；现在也解析 Entrypoint、shell 包装和实际进程参数，仅保存白名单，不保存 Env/API key |
| 现场手工修改 | 支持指定旧项目并复制代码，记录哈希；尤其保留 keepalive 的实际写法 |
| 资源单位 | 去除快照里固定 `/16`，统一读取配置块大小；上下文上限、虚拟逐步预算、客户端并发、未知物理 KV 容量分开记录 |
| 准入与顺序 | 整批提交前检查重复、父依赖、状态、路由、容量和新鲜度；资源投影只比较准入成员，不因列表顺序不同拒绝 |
| 评分 | 记录参考/候选开始与可排名次数、失败原因、decode guard 拒绝；超时后返回的结果仅留诊断，绝不执行 |
| 时钟 | 子进程接收时长并使用本地 deadline；父进程独立限制包含 IPC 的总耗时，不跨进程直接相减单调时间 |
| 动作记录 | 区分请求动作、客户端接受、客户端提交序列；只有与基线的每副本实际提交序列/路由不同才计客户端有效偏离；引擎接受/应用保持未知 |
| 请求与时延 | 每请求独立 X-Request-Id，不改变共享前缀；保存服务响应 ID，检查同一流 ID 一致；新增请求文本 TTFT P95 |
| 报告 | 原始哈希校验后在新目录重生成，原结果不改；旧非基线计数不再写成引擎应用次数 |
| 实验顺序 | 原 96 条件对象和种子不变；R4/λ8、R2/λ16 先行，按组轮换方法位置，第二轮镜像；每四方法追加工作量审计 |
| 连接配置 | R234 默认 keepalive=0，保留已报告的现场绕行设置；不宣称已证明性能收益或根因 |
| 机制放行 | 默认正式 benchmark 在推理前拒绝，明确缺失接口；显式 HTTP 诊断可运行，不将功能检查当机制 PASS |

资源投影排序的反例来自原 NVIDIA 实现；当前 HTTP 适配此前没有那一处列表相等比较，因此本次是补充整批验证与回归测试，不声称已定位现场运行慢的唯一原因。这里的块大小仍是客户端逻辑配置，现场物理块大小必须采集后核对；HTTP 提交数也没有伪装成 running+2×waiting。

## 必须拿到现场信息后继续的工作

1. 匹配实际 vLLM/vLLM-Ascend 分支及 scheduler、KV manager、block pool 源码；确定已有观测接口，或添加最小版本匹配只读 hook。
2. 逐前缀、逐副本读取已计算可复用长度；区分命中、明确缺失、未知/陈旧；服务重启、驱逐必须使旧证据失效。
3. 核对实际 running、waiting、物理 KV 容量及逐步 token 预算；记录引擎对准入/队列动作的接受和应用。HTTP 请求顺序不等于引擎队列顺序。
4. 独立小探针覆盖冷/热、不同副本和命名空间、并发 1/4、16/128 为主的输出长度与 mixed 阶段。训练/验证数据与正式实验分离，冻结 batch-step 模型后再实验。
5. 验证 fork/join 依赖、真实缓存证据、参考和候选完整评分、回退、排空及实际应用动作，全部通过后才放行正式 96 条件。不能以“比基线快 10%”替代机制检查。

当前 HTTP 校准仍是端到端 TTFT/TPOT 近似模型；没有伪造上述原生校准、缓存或引擎应用。默认门禁因此保持关闭，没有读取用户手填 PASS 文件的绕过入口。
